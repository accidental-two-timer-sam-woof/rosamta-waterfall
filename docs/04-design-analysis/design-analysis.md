# 設計分析

## 1. 分析基準

需求範圍與驗收條件以 [SRS 1.1](../02-srs/srs.md) 為準。依 Valente 第 4、5 章，用[初步設計 UML](../03-preliminary-design/uml.md) 的 C1–C4 核對責任與耦合，用 S1–S6 核對各情境的操作順序。依 Royce 圖 5、7 和 Valente 第 8 章，先分析跨平台檔案操作的風險，再用小型原型驗證寫入、接管與回復。設計選擇經團隊審查後，與驗證情境及待定事項一併交給[詳細設計](../05-detailed-design/detailed-design.md)。 [Royce，1970](https://www.praxisframework.org/files/royce1970.pdf) · [Valente 第 4 章](https://softengbook.org/chapter4) · [第 5 章](https://softengbook.org/chapter5) · [第 8 章](https://softengbook.org/chapter8)

第一版須涵蓋全部 `essential` 需求。互動處理、一次列出所有預檢錯誤、依賴檢查、機器可讀輸出與效能目標屬於 `conditional` 需求。團隊評估後確認納入或延後，並依 SRS §2.6 與附錄 A.3 記錄結果。

停止管理涉及宣告與狀態兩份資料。若其中一份寫入失敗或程序中止，下次套用須保留原檔的內容與權限。05 須確保套用讀到一致狀態，或能辨識未完成的停止管理操作。在恢復一致狀態前，受影響項目不得被清除、重新接管或改動，包含宣告已移除但仍有狀態，以及狀態已清除但接管宣告仍在的情況（FR-MAN-025）。

若停止管理在較早的套用計畫執行前成功，該計畫對已停止管理的項目失效，不得改動原檔或恢復其紀錄。05 須確保套用與停止管理的執行及狀態提交彼此協調，例如互斥或驗證計畫版本（FR-MAN-025）。

納入管理須在未占用的位置建立來源副本，建立完成後才新增引用它的 manifest 宣告。若預定位置已占用或在建立時被占用，另選未占用的位置，或回報失敗並保留既有來源及 manifest。05 須定義命名及避免覆寫的建立方式（FR-MAN-023）。

每次規劃使用同一份主機資訊、Profile 啟用結果與狀態紀錄。S3 的比較資訊可取自 S1 交給 `Planner` 的紀錄。執行前若須重檢，應區分規劃時的觀測與執行前的現況。用相同輸入核對預覽與套用的計畫（FR-PLN-006；S1、S3）。

CLI 將計畫與執行回報送到標準輸出，將錯誤與警告送到標準錯誤。預覽和查詢都須維持唯讀。若納入互動功能，只有明確啟用互動且標準輸入連接終端機時才詢問。所有必做功能須在 Linux、Windows、macOS 以一般使用者權限運作，並能以各平台的單一執行檔發佈。初始化取得遠端來源可使用 git（IF-007、IF-008、IF-013、USE-001、USE-002、DC-001、DC-004、PORT-001）。

## 3. 關鍵流程分析

### 3.1 判定目標、接管與清除

`Planner` 先判定啟用的輸出與目標路徑，再按同一套平台路徑規則檢查碰撞與 home 範圍。來源、本機設定、狀態、備份與暫存檔同樣受 home 寫入限制。目標是符號連結時，檢查連結本身。父目錄解析後若使寫入位置超出 home，須攔下操作（FR-MAN-007–010、FR-PLN-009、FR-PLN-010、DC-002、DC-003、SEC-002）。

manifest 指定的使用者範本及原樣複製檔案須以來源目錄為基準。預覽與套用都只可讀取仍位於來源目錄內的這類檔案，範本若支援載入其他來源檔案也受同一限制。遇到越界的相對路徑、符號連結，或讀取時無法確認邊界，應回報來源路徑錯誤並停止該計畫。越界檔案的內容不得進入差異或輸出。內建資源與本機設定仍由各自的載入流程處理。05 須定義各平台在實際讀取時如何維持來源邊界（FR-MAN-005、FR-TPL-006、FR-PLN-003、FR-PLN-007）。

預檢也檢查路徑是否同時被當成一般檔案與目錄。例如兩個輸出分別指向 `~/app` 和 `~/app/settings.toml`，即使都尚未建立，也無法同時套用。遇到這種衝突時，回報涉及的輸出與路徑，整批回傳 `1`，並保留所有既有輸出與狀態檔（FR-PLN-007、FR-APL-008、DC-003）。

預檢須保護來源目錄及其內容、本機設定、狀態檔，以及程式保留的鎖定、備份、暫存和回復位置。啟用輸出若佔用這些位置，即使目標尚不存在或動作為「不變」，仍須攔下整批套用。清除計畫也不得刪除這些位置的既有檔案。失敗時指出輸出與衝突的位置，回傳 `1`，保留既有檔案與狀態。05 須定義保留位置及各平台的路徑別名判定（FR-PLN-007、FR-APL-001、FR-APL-008、DATA-005）。

| 觀察結果 | 決策 | 依據 |
| --- | --- | --- |
| 狀態檔不存在 | 以空紀錄規劃，將既有目標視為未受管理 | REL-003；S1、S2 |
| 狀態檔讀取失敗或損毀 | 預檢失敗，指出狀態檔路徑，保留既有輸出與狀態檔 | REL-004；S1 |
| 一般檔案無紀錄，且內容已符合期望 | 直接記為受管理，保留內容並省略接管備份。之後停用或移除仍適用清除規則 | FR-MAN-021、FR-DRF-012；S2、S4 |
| 一般檔案無紀錄，且內容與期望不同 | 有接管授權時先備份，再寫入並回報備份位置。其餘保留並說明原因 | FR-MAN-018–022；S2 |
| 目標本身是符號連結 | 視為未受管理。有接管授權時備份連結本身，再以一般檔案取代連結。其餘保留連結。兩種情況皆須保護連結所指的檔案 | SEC-002、DC-003；補足 S2 的分流 |
| 原受管理輸出已移除、停用或改路徑 | 未被修改的舊檔刪除並清紀錄。被修改的舊檔預設連同紀錄保留。舊檔已不存在時只清紀錄。已停止管理的輸出保留目標檔，後續清除也須略過 | FR-DRF-012–017、FR-MAN-025；S4 |

套用與清除都須核對舊紀錄、本次目標及父路徑，確認仍是原本受管理的位置。若父目錄在兩次套用間遭替換，即使新的位置仍在 home 內且檔案內容相同，也不能只憑內容比對沿用舊紀錄。無法確認位置時，清除須保留檔案與紀錄並回報原因。仍啟用的輸出則按未受管理的既有檔案處理。內容與期望不同時，有接管授權才可先備份後替換，否則保留檔案。05 須定義如何記錄與比對位置（FR-MAN-019–021、FR-DRF-012–013、FR-DRF-016、DATA-006）。

若啟用中的新輸出與待清除的既有舊輸出佔用同一個正規化路徑，須先釐清該路徑的歸屬，避免清除舊輸出時刪掉新輸出要保留的檔案，或以新內容覆寫使用者修改。第一版提案是在預檢擋下整批套用，包含新輸出動作為「不變」及舊檔應保留的情況。若採此提案，套用回傳 `1`，保留所有輸出與狀態檔，並列出路徑、狀態檔中的舊輸出名稱，以及新輸出名稱和宣告位置。整批阻擋仍待團隊確認（見 §6）。

若舊檔已確認不存在，只剩舊紀錄，新輸出可在同一路徑建立。規劃時將建立新檔與移除舊紀錄視為同一路徑的操作。建立時須保證位置仍空，避免覆寫其間出現的檔案。提交狀態前確認目標仍是本批建立的檔案，再一併移除舊紀錄並加入新紀錄。若位置被外部程式先占用，或本批建立的檔案又被替換，依執行失敗處理，保護外部檔案（FR-DRF-015、FR-APL-001–002）。

### 3.2 Drift 與狀態紀錄

詳細設計方案沿用 C3 的兩份比較基準。接受 drift 時，實際基準記錄目前目標的比較資訊，用來判斷目標是否再被改動。期望基準記錄當時產生結果的比較資訊，用來判斷來源是否產生新內容。只存實際基準就無法判斷後者。狀態檔保存輸出名稱、目標路徑及比較資料，與本機設定一同放在來源目錄外。輸出內容與回復快照各自管理（FR-DRF-001–008、DATA-005、DATA-006、SEC-001；C3、S3）。

假設目標原為 `A`，遭外部修改為 `B`，期望仍為 `A`。接受後實際基準為 `B`，期望基準為 `A`。原樣重跑時維持 `B`。目標再次改為 `C` 時，重新判定 drift。內容已符合本次期望時依 FR-DRF-002 更新紀錄，再依平台與權限宣告判斷是否仍須處理屬性。

若只有來源變更，使期望內容改為 `D`，本分析建議第一版納入 FR-DRF-008。預覽顯示一般更新 `B` → `D`，也能符合 FR-MOD-002 對共用欄位更新的要求。若團隊考慮延後，保留 `B` 與兩份比較基準是待確認的提案。採此方案前須在 SRS 釐清 FR-MOD-002 的適用範圍。若定案允許保留，預覽列為「不變」，說明已接受 drift，來源更新暫緩。

嚴格模式採 UML §12 已確認的優先序。只要有 drift 衝突，就在任何寫入前停止整批套用，包含同時指定的接受或覆寫。須列出每個衝突的輸出名稱與目標路徑，回傳 `1`。嚴格模式下若只有未接管項目被保留，其他項目可照常執行。全部完成或計畫為空回傳 `0`，完成和保留並存回傳 `2`，只有保留回傳 `1`（FR-DRF-009、FR-APL-006–008；S1、S3、S5）。

### 3.3 寫入、儲存與回復

套用開始後，`RecoveryManager` 先取得原狀態檔的回復資訊，再為每個待變更項目保存套用前的內容、適用權限及存在與否。接管備份須在取代目標前完成。寫入新內容時，先備妥完整檔案，再以平台支援的方式替換。輸出未宣告權限時，替換須保留既有檔案的權限，只有權限變更時也不列為 drift。全部目標操作成功後才提交新狀態。若中途操作或提交狀態失敗，回復已變更的目標與原狀態，並回報原錯誤及未能恢復的各路徑和原因。接管備份供使用者取回原檔，批次快照供程式回復（FR-APL-001–005、FR-MAN-016、FR-MAN-019、REL-001、REL-002；S2、S5）。

若較早的項目已接管符號連結，回復須能還原連結本身，並保護它所指的檔案。程序被強制終止時，依 REL-001、REL-002 檢查單一輸出或狀態檔是否保持完整。分別估算期望內容、單次替換的暫存檔、累積的回復快照與接管備份所需的空間，並評估磁碟空間不足時哪些操作可能失敗。

含輸出原文的暫存檔、快照與接管備份，自建立起就須限制其他一般帳號存取。接管備份依保留規則保存。套用完成後清理不再需要的暫存檔與快照。程序中止或回復失敗後可能留下副本，仍須維持存取限制，由 05 定義各平台的保護與清理方式。若納入 SEC-003，備份在受保護位置內仍須保留原檔權限。套用和接受 drift 時，狀態檔都不得存入輸出原文（SEC-001、SEC-003）。

寫入與刪除須確保操作當下的目標及父路徑仍符合預檢的觀測與 home 邊界。若發現路徑遭替換或無法確認操作安全，停止該操作與後續套用，本批已變更的項目進入整批回復。

只變更狀態檔的項目也須在提交時核對目標及父路徑。直接納管須確認檔案仍符合期望，接受 drift 須確認內容仍是使用者同意保留的版本，只清除舊紀錄則須確認舊檔仍不存在。觀測若失效，依執行失敗處理，不提交該筆狀態，也不回報完成（FR-MAN-021、FR-DRF-006、FR-DRF-015、FR-APL-001–002）。

回復也須守住 home 邊界，並確認操作當下的目標及父路徑仍對應本批操作後的預期位置與狀態。例如還原已刪除的檔案前，原父目錄須仍在原位，且目標仍不存在。若與預期不符或無法確認，跳過該路徑，繼續回復其他可安全處理的項目。回報須列出未能回復的各路徑與原因（DC-002、SEC-002、FR-APL-002–004）。

管理與初始化的實際寫入也受 home 邊界約束，包含納入管理時的來源副本、manifest 變更及初始化的暫存與本機設定。若操作當下發現路徑遭替換或無法安全確認，該子指令回報失敗，並保護替代位置的檔案（DC-002、IF-007）。

SRS 假設同一組目標同時只有一個 rosamta 程序在套用，且目標所在檔案系統支援單次操作替換（AS-5、AS-6）。05 須定義各平台如何在實際操作時維持路徑保護，並評估多程序互斥與不支援替換時的診斷。

| 使用者設定格式與編輯 | 選擇支援 UTF-8 和註解的格式，並比較能保留來源格式的語法樹編輯與依來源位置局部修改。前者可集中處理語法與診斷，後者可縮小改動範圍，但須處理不同結構的新增和刪除 | 以含註解、空行、不同縮排與換行的設定測試納入、修改、停止管理與本機設定合併。比較未修改區域的位元組，並確認錯誤可指出位置（IF-010、FR-MAN-029、FR-MAN-030、FR-INI-008） |
| 範本語言 | 比較限制存取能力的現有引擎與小型自訂語法。既有引擎可減少自建語法的成本。自訂語法可直接控制欄位參照的表示，但需自行維護語法、錯誤訊息與相容性 | 驗證渲染與引用查詢能共用一套欄位參照規則，涵蓋條件分支及未啟用輸出。範本能力須維持預覽的限制，並為公開語法與函式建立相容性案例（FR-TPL-001–003、FR-QRY-003、FR-QRY-004、FR-PLN-005、MNT-001） |
| 實作語言與檔案操作 | 先篩選可產出各平台獨立執行檔的工具鏈。共用檔案介面可減少上層對平台的依賴，個別平台的替換、連結與權限行為仍需實測 | 在三平台以一般使用者測試單檔替換、符號連結接管、回復與單一執行檔發佈（DC-001–004、SEC-002、REL-001、REL-002、PORT-001） |

## 5. 驗證情境

表列案例供 05 的小型原型和 [06 測試計畫](../06-test-plan/test-plan.md) 使用。決策規則可先用固定輸入檢查。檔案替換、權限、連結與程序中止須在實際檔案系統驗證。

| 案例 | 操作與預期結果 | 需求 |
| --- | --- | --- |
| A1 欄位來源與輸出清單 | 讓四層都設定同一欄位，逐層移除設定後檢查值及來源。另讓兩個同層來源設定同欄位，檢查預檢失敗與來源診斷。完整清單須列出內建與未啟用輸出，模組查詢須列出所有引用，包含未啟用輸出。若納入欄位查詢，再逐一驗證每個欄位的查詢結果均包含所有引用它的輸出 | FR-PRF-009–013、FR-MAN-026、FR-QRY-001–002、FR-QRY-004 |
| A2 預覽與預檢 | 在相同輸入下先預覽再套用，比對逐項動作。令最後一項與另一筆 manifest 宣告的路徑碰撞，再測兩個輸出分別指向尚不存在的 `~/app` 和 `~/app/settings.toml`。兩種衝突皆須回傳 `1` 並列出涉及的輸出和位置，所有輸出與狀態檔均不寫入。另準備只改輸出名稱、路徑與期望內容相同的案例，分別測試未改過與已手動修改的舊檔，並讓同批另一個獨立輸出待更新。若採整批阻擋提案，驗證回傳 `1`、兩個名稱都有回報，且兩個目標及狀態檔都不變 | FR-PLN-004、FR-PLN-006–007、FR-PLN-009–010、FR-DRF-012–013、DC-003 |
| A3 納管及連結接管 | 移除狀態檔後以內容相同的一般檔案重新納管。另以指向 home 外檔案的連結分別測試保留及接管，即使所指檔案的內容符合期望，仍依連結規則處理。接管時回報可用備份，該目標成為一般檔案，連結原本指向的檔案不變。另在兩次套用間，以 home 內另一個含同名同內容檔案的目錄替換父目錄。修改仍啟用輸出的範本後，分別驗證未授權接管時保留替代檔，授權接管時先備份再替換 | REL-003、FR-MAN-019–021、SEC-002 |
| A4 接受與嚴格模式 | 按 §3.2 驗證接受後重跑及再次外部修改。讓三個啟用輸出共用 `theme` 的前景色，其中一個曾接受 drift。只改前景色時，納入 FR-DRF-008 的方案應預覽三個更新，套用後三個輸出皆使用新值。若 SRS 定案允許保留例外，改驗另兩個輸出已更新、接受過的輸出與基準維持原樣，且預覽說明暫緩原因。另在同批安排兩個 drift 衝突及一個無衝突且待更新的輸出，分別以嚴格模式指定接受、覆寫。確認所有目標與狀態檔都不變、逐項列出衝突名稱與路徑，並回傳 `1`。若只有未接管項目被保留，確認另一項照常完成且回傳 `2` | FR-MOD-002、FR-DRF-001、FR-DRF-005–009、FR-APL-007、FR-APL-008 |
| A5 清除與停止管理 | 驗證未改、已改及不存在的舊檔分別會被刪除、保留或只移除紀錄。下次套用前，把舊輸出的父目錄換成指向 home 內另一個含相同檔案的目錄。停用後確認替代檔案與舊紀錄都保留。停止管理內建輸出後，重新載入仍須保留原檔，且不再套用。另準備未改的舊檔，以及已手改且宣告接管的舊檔，在停止管理的兩次寫入間注入失敗或中止，再套用並核對原檔的存在狀態、內容及權限。最後，建立會更新該目標的計畫，先完成停止管理再執行舊計畫，確認原檔未改，紀錄也未恢復 | FR-DRF-012、FR-DRF-013、FR-DRF-015、FR-DRF-016、FR-MAN-025 |
| A6 回復及單檔完整性 | 注入中途寫入失敗、狀態提交失敗與部分回復失敗，檢查目標及原狀態的回復和診斷。目標涵蓋一般檔案與原為連結的項目。在替換時強制終止程序，檢查輸出與狀態檔各自保有完整的舊內容或新內容。在 Linux 和 macOS 將未宣告權限的既有輸出改為 `0600`，確認只改權限不會被判定為 drift。再更新該檔案內容，確認權限仍為 `0600` | FR-APL-002–004、FR-APL-008、FR-MAN-016、REL-001、REL-002、SEC-002 |
| A7 初始化失敗與首套用 | 來源位置已有檔案時指定遠端，應回傳 `1`，原檔不變，且不寫入輸出。下載期間在原本空的正式位置新增檔案，確認回傳 `1`、新增檔案與本機設定不變，且未進入首次套用。遠端取得失敗時應回報位址與原因，維持正式來源、本機設定及輸出的原狀。遠端下載成功後、移入正式位置前，另將其父目錄換成指向 home 外的連結，確認回傳 `1`、外部位置沒有新增或修改檔案，且未進入首次套用。以測試 repo 驗證 HTTPS、SSH，以及首次套用保留一項、完成一項時回傳 `2` | DC-002、IF-012、FR-INI-001、FR-INI-009–011 |
| A8 時間與空間 | 若納入效能目標，依 SRS 在參考機器上先套用一次，再量測 500 個輸出皆不變時的 10 次套用。執行時間的中位數須小於 1 秒。另測試多個大檔與磁碟空間不足的情境，觀察暫存及快照的用量和回復結果 | PERF-001、FR-APL-002、REL-001、REL-002 |
| A9 範本與原樣複製 | 用含條件分支的範本核對渲染與引用查詢，並驗證覆寫單一內建範本時其他輸出維持原樣。用含範本符號與非 UTF-8 位元組的來源驗證原樣複製，輸出須與來源逐位元組相同。對範本與原樣複製來源分別測試越界的相對路徑、越界連結，以及最後一次路徑檢查通過後、開檔前換成越界連結。若來源越界，預覽與套用都須回報路徑錯誤，差異及輸出不含外部檔案的內容，套用不寫入輸出與狀態檔 | FR-MAN-005、FR-TPL-003、FR-TPL-006、FR-PLN-003、FR-PLN-007、FR-QRY-003、FR-QRY-004 |
| A10 預檢後路徑遭替換 | 分別在預檢剛通過，以及最後一次路徑檢查通過但尚未寫入或刪除時，嘗試把父目錄換成指向 home 外的連結。回復時也在最後一次檢查通過後、實際操作前嘗試替換，並加入 home 內另一個含同名檔案的目錄。若替換成功，確認停止操作受影響的路徑、回傳 `1`，且替代位置的檔案未被修改或刪除。若已有變更，確認可安全回復的路徑已還原，其餘路徑及原因逐項回報 | DC-002、SEC-002、FR-APL-002–004、FR-APL-008 |
| A11 內部路徑碰撞 | 將啟用輸出的目標指向狀態檔位置，分別測試狀態檔尚未建立、已有內容及可辨識的路徑別名。另以舊狀態指向受保護位置，觸發清除計畫。確認預檢指出衝突並回傳 `1`，既有檔案與狀態不變，原本不存在的狀態檔也不會建立 | FR-PLN-007、FR-APL-001、FR-APL-008、DATA-005 |
| A12 管理指令的路徑保護 | 執行納入管理，於來源副本即將寫入前將其父目錄換成指向 home 外的連結。確認指令回傳 `1`，且外部目錄沒有新增檔案，既有同名檔案亦維持原樣。另讓其他輸出引用預定位置的既有來源檔，並測試在最後一次檢查後才占用預定位置。兩種情境皆須保留原檔與既有宣告，成功時新宣告應引用另一處新副本，失敗時則不新增宣告 | DC-002、FR-MAN-023、IF-007 |
| A13 輸出原文與副本 | 在套用的輸出與接受 drift 的實際內容各放一個標記字串，兩次操作後分別檢查狀態檔，確認都找不到原文。分別在暫存檔、快照與備份建立後中止程序，驗證即使留下副本，其他一般帳號也無法讀取。若納入備份權限保留，再驗證備份的原權限 | SEC-001、SEC-003、FR-DRF-006 |
| A14 只更新狀態的項目 | 分別規劃直接納管、接受 drift 和移除不存在的舊檔紀錄。提交前改動原本符合期望的檔案、改動已確認接受的內容，或讓舊檔重現。三種情境皆須回報執行失敗，不提交過時的紀錄，也不將項目列為完成 | FR-MAN-021、FR-DRF-006、FR-DRF-015、FR-APL-001–002、FR-APL-008 |
| A15 新輸出沿用已不存在的舊路徑 | 保留舊狀態紀錄、移除舊檔，讓新輸出沿用同一路徑。套用後應有新檔與新紀錄，舊紀錄應移除。另在最後一次確認位置為空後、實際建立前，由外部程式先寫入同名檔案。再測狀態提交前由外部程式替換本批建立的檔案。兩種情境均須回報失敗、保留外部檔案，且不提交新的狀態 | FR-DRF-015、FR-APL-001–002、FR-APL-008 |

## 6. 文件對齊與交接

| 對齊事項 | 04 採用的依據與後續處理 |
| --- | --- |
| 未受管理的判定 | 依 REL-003、FR-MAN-021、SEC-002 與 §3.1。SRS 詞彙表可另行對齊，明確區分狀態紀錄、一般檔案與符號連結 |
| 整批預檢與錯誤彙整 | FR-PLN-007 的寫入前檢查是必做。S1 所述一次收集所有錯誤依 USE-004 的 `conditional` 分期 |
| 完整輸出清單、預覽與接管回報 | 05 依 §2 的查詢責任與回報內容補上介面和資料模型，對應 FR-MAN-026、FR-PLN-003、FR-MAN-019 |
| 嚴格模式與互動 | 嚴格模式優先依 UML §12。非嚴格模式下明確處理選項與互動提示的優先序，待互動功能納入時確認 |
| 預覽與套用的一致性 | FR-PLN-006 明列來源、本機設定及目標路徑。狀態紀錄可在目標內容不變時更新，例如接受 drift。驗證時也固定狀態、主機資訊及適用選項，由團隊確認是否在 SRS 補述比較前提 |
| 同一路徑的舊輸出與新輸出 | FR-PLN-009 驗證的是兩筆 manifest 宣告的碰撞，FR-DRF-013 要求保留使用者修改過的舊檔。改名時舊輸出來自狀態檔，團隊須確認是否採用 §3.1 的整批阻擋提案，以及同批其他輸出能否照常更新，再定案 A2 的預期結果 |
| 來源變更與分期 | SRS §3.2.7 簡介描述來源變更後的一般更新，FR-DRF-008 則列為 `conditional`。若考慮延後，團隊須先釐清保留已接受輸出是否需要在必做的 FR-MOD-002 增列例外，再定案 A4 的預期結果並對齊 SRS |
| 查詢驗收與分期 | FR-QRY-004 的驗收文字同時引用模組與欄位查詢。A1 將模組查詢的完整性列為必驗，欄位查詢納入時才加驗其完整性。欄位查詢延後時的正式驗收方式由團隊確認並透過 SRS 修訂 |

05 須定義設定、範本及執行介面，並完成 UML §12 的五項設計，包括接管備份的命名及保留規則、比較資料的格式與演算法、預檢後重檢與多程序協調、平台路徑與連結檢查，以及內建輸出停止管理的持久化表示。06 依 SRS 的需求編號與驗收條件編寫案例，納入本文件的分支及故障情境。
