# 設計分析

## 1. 分析基準

需求範圍與驗收條件以 [SRS 1.1](../02-srs/srs.md) 為準。系統責任與耦合以[初步設計 UML](../03-preliminary-design/uml.md) 的 C1–C4 為準，操作順序對照 S1–S6。設計選擇由團隊審查。[詳細設計](../05-detailed-design/detailed-design.md)須以小型原型驗證跨平台寫入、接管與回復。分析方法參考 Valente 第 4、5、8 章與 Royce 圖 5、7。[Royce，1970](https://cse.msu.edu/~cse435/Homework/HW3/royce1970.pdf) · [Valente 第 4 章](https://softengbook.org/chapter4) · [第 5 章](https://softengbook.org/chapter5) · [第 8 章](https://softengbook.org/chapter8)

第一版須涵蓋全部 `essential` 需求。互動處理、一次列出所有預檢錯誤、依賴檢查、機器可讀輸出與效能目標屬於 `conditional` 需求。團隊評估後確認納入或延後，並依 SRS §2.6 與附錄 A.3 記錄結果。

停止管理涉及宣告與狀態兩份資料。若其中一份寫入失敗或程序中止，下次套用須保留原檔的內容與權限。05 須確保套用讀到一致狀態，或能辨識未完成的停止管理操作。在恢復一致狀態前，受影響項目不得被清除、重新接管或改動，包含宣告已移除但仍有狀態，以及狀態已清除但接管宣告仍在的情況（FR-MAN-025）。

若停止管理在較早的套用計畫執行前成功，該計畫對已停止管理的項目失效，不得改動原檔或恢復其紀錄。05 須確保套用與停止管理的執行及狀態提交彼此協調，例如互斥或驗證計畫版本（FR-MAN-025）。

納入管理須在未占用的位置建立來源副本，建立完成後才新增引用它的 manifest 宣告。若預定位置已占用或在建立時被占用，另選未占用的位置，或回報失敗並保留既有來源及 manifest。05 須定義命名及避免覆寫的建立方式（FR-MAN-023）。

每次規劃使用同一份主機資訊、Profile 啟用結果與狀態紀錄。預檢通過前須備妥啟用輸出的期望內容。執行期參照須對應該版內容，套用時不再從可能變動的來源重讀或渲染。若無法取得原先確認的內容，依執行失敗處理。S3 的比較資訊可取自 S1 交給 `Planner` 的紀錄。執行前若須重檢，應區分規劃時的觀測與執行前的現況。用相同輸入核對預覽與套用的計畫（FR-PLN-006；S1、S3）。

CLI 將計畫與執行回報送到標準輸出，將錯誤與警告送到標準錯誤。預覽和查詢都須維持唯讀。若納入互動功能，只有明確啟用互動且標準輸入連接終端機時才詢問。所有必做功能須在 Linux、Windows、macOS 以一般使用者權限運作，並能以各平台的單一執行檔發佈。初始化取得遠端來源可使用 git（IF-007、IF-008、IF-013、USE-001、USE-002、DC-001、DC-004、PORT-001）。

## 3. 關鍵流程分析

### 3.1 判定目標、接管與清除

`Planner` 先判定啟用的輸出與目標路徑，再按同一套平台路徑規則檢查碰撞與 home 範圍。來源、本機設定、狀態、備份與暫存檔同樣受 home 寫入限制。目標是符號連結時，檢查連結本身。父目錄解析後若使寫入位置超出 home，須攔下操作（FR-MAN-007–010、FR-PLN-009、FR-PLN-010、DC-002、DC-003、SEC-002）。

預覽、套用與引用查詢讀取 manifest 指定的使用者範本或原樣複製來源時，實際讀取的檔案須位於來源目錄內。若範本可載入其他來源檔案，也受相同限制。遇到越界的相對路徑、符號連結，或讀取時無法確認邊界，應回報來源路徑錯誤並停止該計畫或查詢。越界檔案的內容不得進入差異、輸出或查詢結果。內建資源與本機設定仍由各自的載入流程處理。05 須定義各平台在實際讀取時如何維持來源邊界及檔案類型檢查（FR-MAN-005、FR-TPL-006、FR-PLN-003、FR-PLN-007、FR-QRY-003、FR-QRY-004）。

預檢也檢查路徑是否同時被當成一般檔案與目錄。例如兩個輸出分別指向 `~/app` 和 `~/app/settings.toml`，即使都尚未建立，也無法同時套用。遇到這種衝突時，回報涉及的輸出與路徑，整批回傳 `1`，並保留所有既有輸出與狀態檔（FR-PLN-007、FR-APL-008、DC-003）。

預檢須保護來源目錄及其內容、本機設定、狀態檔，以及程式保留的鎖定、備份、暫存和回復位置。啟用輸出若佔用這些位置，即使目標尚不存在或動作為「不變」，仍須攔下整批套用。清除計畫也不得刪除這些位置的既有檔案。失敗時指出輸出與衝突的位置，回傳 `1`，保留既有檔案與狀態。05 須定義保留位置及各平台的路徑別名判定（FR-PLN-007、FR-APL-001、FR-APL-008、DATA-005）。

| 觀察結果 | 決策 | 依據 |
| --- | --- | --- |
| 狀態檔不存在 | 以空紀錄規劃，將既有目標視為未受管理 | REL-003；S1、S2 |
| 狀態檔讀取失敗或損毀 | 預檢失敗，指出狀態檔路徑，保留既有輸出與狀態檔 | REL-004；S1 |
| 一般檔案無紀錄，且內容已符合期望 | 直接記為受管理，保留內容並省略接管備份。之後停用或移除仍適用清除規則 | FR-MAN-021、FR-DRF-012；S2、S4 |
| 一般檔案無紀錄，且內容與期望不同 | 有接管授權時先備份，再寫入並回報備份位置。其餘保留並說明原因 | FR-MAN-018–022；S2 |
| 目標本身是符號連結 | 視為未受管理。有接管授權時備份連結本身，再以一般檔案取代連結。其餘保留連結。兩種情況皆須保護連結所指的檔案 | SEC-002、DC-003；補足 S2 的分流 |
| 應為一般檔案的來源或目標是目錄、FIFO、裝置檔或通訊端 | 預檢須先辨識類型。開檔時須避免因不支援的類型而阻塞，並在讀取內容前核對實際檔案類型。來源連結解析後須確認是一般檔案。遇到不支援的類型時，停止讀取、接管或清除。預覽與套用皆指出路徑及類型並回傳 `1`，保留原項目、其他輸出與狀態檔 | FR-PLN-007、FR-APL-008、SEC-002、DC-003 |
| 原受管理輸出已移除、停用或改路徑 | 先判定舊目標的類型。若舊檔已被換成符號連結，保留連結、連結所指檔案與舊紀錄，並回報原因。舊目標仍是一般檔案時，未被修改的舊檔刪除並清紀錄，被修改的舊檔預設連同紀錄保留。舊檔已不存在時只清紀錄。已停止管理的輸出保留目標檔，後續清除也須略過 | FR-DRF-012–017、FR-MAN-025、SEC-002；S4 |

套用與清除都須核對舊紀錄、本次目標及父路徑，確認仍是原本受管理的位置。若父目錄在兩次套用間遭替換，即使新的位置仍在 home 內且檔案內容相同，也不能只憑內容比對沿用舊紀錄。無法確認位置時，清除須保留檔案與紀錄並回報原因。仍啟用的輸出則按未受管理的既有檔案處理。內容與期望不同時，有接管授權才可先備份後替換，否則保留檔案。05 須定義如何記錄與比對位置（FR-MAN-019–021、FR-DRF-012–013、FR-DRF-016、DATA-006）。

若啟用中的新輸出與待清除的既有舊輸出佔用同一個正規化路徑，須先釐清該路徑的歸屬，避免清除舊輸出時刪掉新輸出要保留的檔案，或以新內容覆寫使用者修改。第一版提案是在預檢擋下整批套用，包含新輸出動作為「不變」及舊檔應保留的情況。若採此提案，套用回傳 `1`，保留所有輸出與狀態檔，並列出路徑、狀態檔中的舊輸出名稱，以及新輸出名稱和宣告位置。整批阻擋仍待團隊確認（見 §6）。

若舊檔已確認不存在，只剩舊紀錄，新輸出可在同一路徑建立。規劃時將建立新檔與移除舊紀錄視為同一路徑的操作。建立時須保證位置仍空，避免覆寫其間出現的檔案。提交狀態前確認目標仍是本批建立的檔案，再一併移除舊紀錄並加入新紀錄。若位置被外部程式先占用，或本批建立的檔案又被替換，依執行失敗處理，保護外部檔案（FR-DRF-015、FR-APL-001–002）。

### 3.2 Drift 與狀態紀錄

狀態紀錄沿用 C3 的兩份比較基準。接受 drift 時，實際基準記錄目前目標的比較資訊，用來判斷目標是否再被改動。期望基準記錄當時產生結果的比較資訊，用來判斷來源是否產生新內容。只存實際基準就無法判斷後者。狀態檔保存輸出名稱、目標路徑及比較資料，與本機設定一同放在來源目錄外。輸出內容與回復快照各自管理（FR-DRF-001–008、DATA-005、DATA-006、SEC-001；C3、S3）。

假設目標原為 `A`，遭外部修改為 `B`，期望仍為 `A`。接受後實際基準為 `B`，期望基準為 `A`。原樣重跑時維持 `B`。若目標再次被改動，重新判定 drift。若改動後的內容已符合本次期望，依 FR-DRF-002 更新紀錄，再依平台與權限宣告判斷是否仍須處理屬性。若只有來源變更，且新期望恰好等於未再改動的 `B`，依 S3 更新期望基準，保留目標內容與實際基準。

若只有來源變更，使期望內容改為 `D`，第一版建議納入 FR-DRF-008。預覽顯示一般更新 `B` → `D`，也能符合 FR-MOD-002 對共用欄位更新的要求。若團隊考慮延後，且 `B` 仍與新期望不同，保留 `B` 與兩份比較基準是待確認的提案。採此方案前須在 SRS 釐清 FR-MOD-002 的適用範圍。若定案允許保留，預覽列為「不變」，說明已接受 drift，來源更新暫緩。

嚴格模式採 UML §12 已確認的優先序。只要有 drift 衝突，即使同時指定接受或覆寫，也須在寫入輸出或狀態檔前停止整批套用。須列出每個衝突的輸出名稱與目標路徑，回傳 `1`。嚴格模式下若只有未接管項目被保留，其他項目可照常執行。全部完成或計畫為空回傳 `0`，完成和保留並存回傳 `2`，只有保留回傳 `1`（FR-DRF-009、FR-APL-006–008；S1、S3、S5）。

### 3.3 寫入、儲存與回復

套用開始後，`RecoveryManager` 先取得原狀態檔的回復資訊，再為每個待變更項目保存套用前的內容、適用權限及存在與否。接管備份須在取代目標前完成。寫入新內容時，先備妥完整檔案，再以平台支援的方式替換。輸出未宣告權限時，替換須保留既有檔案的權限，只有權限變更時也不列為 drift。全部目標操作成功後才提交新狀態。批次在目標重檢通過且 `StateStore.saveAtomically` 回報成功後完成。免寫狀態時，目標與原狀態皆通過最後重檢後完成。狀態檔已替換但必要的寫入確認仍失敗時，仍依 S5 進入回復。凡完成前發生可偵測的執行錯誤，回復已變更的目標與原狀態，並回報原錯誤及未能恢復的各路徑和原因。接管備份供使用者取回原檔，批次快照供程式回復（FR-APL-001–005、FR-MAN-016、FR-MAN-019、REL-001、REL-002；S2、S5）。

若本批先前接管了符號連結，回復須能還原連結本身，並保護它所指的檔案。程序被強制終止時，依 REL-001、REL-002 檢查單一輸出或狀態檔是否保持完整。分別估算期望內容、單次替換的暫存檔、累積的回復快照與接管備份所需的空間，並評估磁碟空間不足時哪些操作可能失敗。

含輸出原文的暫存檔、快照與接管備份，自建立起就須限制其他一般帳號存取。接管備份依保留規則保存。回復所需的資料須保留到批次完成或回復結束。其後清理不再需要的暫存檔與快照。批次完成後，清理錯誤另行回報，已提交的結果仍有效。程序中止或回復失敗後可能留下副本，仍須維持存取限制，由 05 定義各平台的保護與清理方式。若納入 SEC-003，備份在受保護位置內仍須保留原檔權限。套用和接受 drift 時，狀態檔都不得存入輸出原文（SEC-001、SEC-003）。

擷取回復快照、製作接管備份、寫入與刪除時，須確認實際操作的目標及父路徑仍符合預檢記錄的位置及存在狀態，且位於 home 內。若檔案已存在，也須確認實際操作的檔案類型及身分符合預檢所見。擷取快照或備份時，先確認實際開啟的檔案，再讀取內容。目標是符號連結時只保存連結本身。須以實際擷取的快照與接管備份核對規劃時的版本，包含內容及適用權限。清除或覆寫前也須核對實際目標仍符合該版本。即使檔案身分未變，只要擷取或操作前發現版本不同，原計畫即失效。若觀測失效或無法確認操作安全，停止該操作與後續套用，並回復本批已變更的項目（DC-002、DC-003、SEC-002、FR-APL-002–004、FR-MAN-019、FR-DRF-013）。

建立或更新時，須從本批實際寫入的檔案取得身分，並保留內容與適用屬性的比較資料供本批重檢。所有預定回報完成的項目都須重檢目標及父路徑。建立或更新的檔案須仍是本批寫入的檔案，且內容與適用屬性仍符合本批結果。已刪除的檔案須仍不存在。計畫為「不變」且不更新紀錄的項目，也須核對規劃時的檔案身分、內容及適用的宣告屬性。目標的重檢條件須維持到批次完成。若觀測失效，停止提交或完成判定，依執行失敗處理（FR-APL-001–004、FR-APL-006）。

只變更狀態檔的項目也適用上述提交規則，須核對目標及父路徑的位置、存在狀態，以及既有檔案的身分。直接納管或因內容已符合期望而只更新紀錄時，須確認檔案仍符合期望。接受 drift 須確認內容仍是使用者同意保留的版本。只清除舊紀錄時，須確認舊檔仍不存在。對仍存在的目標，納入比較且適用於目前平台的宣告屬性也須符合規劃結果，直到批次完成。觀測若失效，依執行失敗處理，回報該項未完成（FR-MAN-015、FR-MAN-021、FR-DRF-002、FR-DRF-006、FR-DRF-015、FR-APL-001–002）。

回復也須守住 home 邊界，並確認操作當下的目標及父路徑仍對應本批操作後的位置與狀態。回復建立或更新的檔案前，須確認檔案身分、內容及適用屬性仍符合本批結果。還原已刪除的檔案前，須確認原父目錄仍在原位，且目標仍不存在。讀取快照時，須確認實際讀取的副本仍是本批在受保護位置保存的完整快照。若任一條件不符或無法確認，保留現況，繼續回復其他可安全處理的項目。回報須列出未能回復的各路徑與原因（DC-002、SEC-002、FR-APL-002–004）。

`StateStore` 首次載入、擷取原狀態、提交及回復時，須核對實際操作的狀態檔與父路徑、home 邊界，以及該步驟預期的存在狀態。狀態檔存在時，須核對實際檔案的類型及身分。首次載入的狀態作為規劃基準。擷取時須核對實際保存的回復副本與首次載入的版本相符。替換前須確認當前狀態仍符合原版本。替換後須確認狀態檔仍為本批寫入的版本，才可回報提交成功。若無須寫入新狀態，仍須確認本批依賴的原狀態版本有效，直到判定批次完成。回復前須確認取用的副本仍是本批保存的完整版本，並核對目前狀態是否符合本批操作後的結果。若原狀態未受本批改動，無須回寫。若狀態檔或父路徑已被外部改動或無法確認，保留現況、回報失敗，並繼續回復可安全處理的輸出（DC-002、SEC-002、FR-APL-001–004、REL-002、REL-004）。

管理與初始化的實際寫入也受 home 邊界約束，包含納入管理時的來源副本、manifest 變更及初始化的暫存與本機設定。若操作當下發現路徑遭替換或無法安全確認，該子指令回報失敗，並保護替代位置的檔案（DC-002、IF-007）。

SRS 假設同一組目標同時只有一個 rosamta 程序在套用，且目標所在檔案系統支援單次操作替換（AS-5、AS-6）。05 須驗證各平台如何將重檢與實際操作連在一起，並依各階段應有的狀態版本，將目標和狀態檔的重檢條件維持到批次完成。也須評估多程序互斥與不支援替換時的診斷。若平台無法提供所需保護，須由團隊先確認支援條件、失敗行為及是否修訂 SRS。

## 5. 驗證情境

決策規則可用固定輸入驗證。檔案替換、權限、連結與程序中止須在實際檔案系統驗證。以同步點確認故障注入發生在指定步驟。若平台擋下外部操作，須驗證阻擋確實生效，以及原操作仍依計畫完成或依原有錯誤回報。注入未到達指定步驟時，案例須重測。

| A1 欄位來源與輸出清單 | 讓四層都設定同一欄位，逐層移除設定後檢查值及來源。另讓兩個同層來源設定同欄位，檢查預檢失敗與來源診斷。完整清單須列出內建與未啟用輸出，模組查詢須列出所有引用，包含未啟用輸出。若納入欄位查詢，再逐一驗證每個欄位的查詢結果均包含所有引用它的輸出 | FR-PRF-009–013、FR-MAN-026、FR-QRY-001–002、FR-QRY-004 |

| A10 預檢後路徑遭替換 | 分別在預檢剛通過，以及最後一次路徑檢查通過但尚未寫入或刪除時，嘗試把父目錄換成指向 home 外的連結。回復時也在最後一次檢查通過後、實際操作前嘗試替換，另測試父目錄被換成 home 內另一個含同名檔案的目錄。若替換成功，確認指令停止對受影響路徑的操作並回傳 `1`，且替代位置的檔案未被修改或刪除。若已有變更，確認可安全回復的路徑已還原，其餘路徑及原因逐項回報 | DC-002、SEC-002、FR-APL-002–004、FR-APL-008 |
| A11 內部路徑碰撞 | 將啟用輸出的目標指向狀態檔位置，分別測試狀態檔尚未建立、已有內容及可辨識的路徑別名。再針對來源、本機設定及各類保留位置重測，包含輸出動作為「不變」的情境。另以舊狀態指向受保護位置，觸發清除計畫。確認預檢指出衝突並回傳 `1`，既有檔案與狀態不變，原本不存在的狀態檔也不會建立 | FR-PLN-007、FR-APL-001、FR-APL-008、DATA-005 |
| A12 管理指令的路徑保護 | 執行納入管理，於來源副本即將寫入前將其父目錄換成指向 home 外的連結。確認指令回傳 `1`，且外部目錄沒有新增檔案，既有同名檔案亦維持原樣。另讓其他輸出引用預定位置的既有來源檔，並測試在最後一次檢查後才占用預定位置。兩種情境皆須保留原檔與既有宣告，成功時新宣告應引用另一處新副本，失敗時則不新增宣告。另在 manifest 即將寫入時替換其父目錄，確認回報失敗且替代位置的檔案不變 | DC-002、FR-MAN-023、IF-007 |
| A13 輸出原文與副本 | 依 SEC-001 用含標記字串的輸出測試套用，並對接受 drift 的實際內容重測。核對狀態檔格式與內容，確認找不到標記字串，也沒有可還原的輸出原文。分別在暫存檔、快照與備份建立時及中止程序後，以其他一般帳號測試存取，確認副本受保護。若納入備份權限保留，再驗證備份的原權限 | SEC-001、SEC-003、FR-DRF-006 |
| A14 只更新狀態的項目 | 分別規劃直接納管、接受 drift、目標內容已符合新期望而須更新紀錄，以及移除不存在的舊檔紀錄。分別在重檢前及最後一次目標重檢後、狀態替換前，依案例改動原本符合期望的檔案、改動已確認接受的內容，或讓舊檔重現。若納入 FR-MAN-015，在 Linux 或 macOS 測試原本符合 `0600` 的待納管檔及待接受 drift 檔案。於最後一次目標重檢後、狀態替換前，只將權限改為 `0644`。以上改動若成功，確認套用保留外部改動並回報執行失敗，不提交過時的紀錄，也不將項目列為完成 | FR-MAN-015、FR-MAN-021、FR-DRF-002、FR-DRF-006、FR-DRF-015、FR-APL-001–002、FR-APL-008 |
| A15 新輸出沿用已不存在的舊路徑 | 保留舊狀態紀錄、移除舊檔，讓新輸出沿用同一路徑。套用後應有新檔與新紀錄，舊紀錄應移除。另在最後一次確認位置為空後、實際建立前，由外部程式先寫入同名檔案。再測狀態提交前由外部程式替換本批建立的檔案。兩種情境均須回報失敗、保留外部檔案，且不提交新的狀態 | FR-DRF-015、FR-APL-001–002、FR-APL-008 |
| A16 快照與接管備份的讀取 | 先讓同批另一項完成寫入。分別在擷取快照及製作接管備份的最後一次路徑檢查後、開檔前，把父目錄換成另一個含同名檔案的目錄。替代檔案的內容須與原檔不同。若換目錄成功，於原定寫入前換回，確認套用未讀取替代檔案的內容、回傳 `1`、保留原檔與替代檔，並回復其他可安全處理的項目。再於擷取快照或接管備份時直接改動原檔內容，維持到擷取或核對結束才改回。若改動成功，確認套用回傳 `1`、停止變更該目標、保留原狀態，並回復同批已變更且可安全處理的項目。再於擷取完成後、核對副本前把原檔改回，確認仍能拒絕錯誤或混有不同版本的副本，並得到相同的失敗結果。以支援權限設定的平台重測，只改動原檔權限。另驗證成功接管的備份可取回規劃時的原檔版本。最後在回復前替換或破壞某項快照，確認不使用該快照、回報未能回復的路徑與原因，並繼續回復其他項目 | DC-002、SEC-002、FR-APL-002–004、FR-APL-008、FR-MAN-019 |
| A17 寫入後至判定完成前的外部變更 | 分別讓一般建立及更新操作成功，在寫入完成後、第一次依目標路徑查驗身分之前，讓外部程式以內容相同的另一個檔案替換目標。另在最後一次目標重檢後、狀態替換前重測。另準備覆寫後兩份比較基準皆無須變更的案例。先在不注入故障時確認覆寫成功，並觀察狀態檔未提交。再用相同設定，在最後一次重檢後、判定批次完成前注入同內容替換。若替換成功，套用須回傳 `1`，保留原狀態及外部替換的檔案，且不將該項列為完成。其他可安全回復的項目仍須還原。再沿用不提交狀態的設定，在最後一次狀態重檢後、判定完成前從狀態檔移除該筆紀錄。若移除成功，套用須回傳 `1`、保留外部狀態改動、回復可安全處理的輸出，並回報該項未完成 | FR-APL-001–004、FR-APL-006、FR-APL-008 |
| A18 不支援的檔案類型 | 分別將來源、套用目標與清除目標換成目錄，並在支援 FIFO 的平台用無寫入端的 FIFO 重測。預覽與套用須在讀取內容前停止，回報路徑及類型並回傳 `1`。原項目的類型與路徑、其他輸出及狀態檔均維持原樣。再於最後一次檢查後、開檔或操作前換入特殊檔案。若換入成功，確認指令回傳 `1`，保留外部換入的檔案並回復其他可安全處理的項目。各次均須在測試時限內結束 | FR-PLN-007、FR-APL-002–004、FR-APL-008、SEC-002、DC-003 |
| A19 清除或覆寫前就地修改 | 分別規劃清除未修改的舊檔和更新仍啟用的輸出。第一次在預檢後、重檢前修改目標。第二次在最後一次內容核對後、實際清除或覆寫前修改。兩次均在同一檔案上寫入不同內容。若修改成功，套用須回傳 `1`，保留外部修改及原狀態，並回復其他可安全處理的項目 | FR-DRF-012–013、FR-APL-001–004、FR-APL-008 |
| A20 狀態檔操作遇到路徑替換 | 分別在首次載入狀態、擷取原狀態及提交時，於最後一次路徑檢查後、實際操作前替換狀態檔的父目錄。回復案例先讓本批替換狀態檔，再讓 `saveAtomically` 的寫入確認失敗，再於回復的最後一次路徑檢查後、回寫前替換父目錄。各情境都測指向 home 外的連結及 home 內的替代目錄。若替換成功，確認套用回傳 `1`，替代位置的狀態檔內容未被讀取或改動，也沒有新檔。回報原狀態是否可安全保留或還原，其他可安全處理的輸出須回復 | DC-002、SEC-002、FR-APL-001–004、FR-APL-008、REL-002、REL-004 |
| A21 回復前就地修改輸出 | 分別完成建立與更新，再讓同批另一項失敗以觸發回復。分別在回復重檢前，以及最後一次內容核對後、實際回復前直接改動同一檔案的內容。若改動成功，確認套用回傳 `1`、保留外部修改，並回報未回復的路徑與原因。其他可安全處理的項目須回復。以支援權限設定的平台重測兩個時點，只改動檔案權限 | FR-APL-002–004、FR-APL-008 |
| A22 清除後路徑重新占用 | 完成清除後，分別在重檢前及最後一次目標重檢後、狀態替換前，在同一路徑建立另一個檔案。若建立成功，確認套用回傳 `1`，保留外部檔案與原狀態，回報清除未完成。再讓其他項目失敗以觸發回復，在回復最後一次確認路徑為空後、還原舊檔前建立另一個檔案。若建立成功，確認外部檔案保留，並回報該路徑無法回復。兩種情境皆須回復其他可安全處理的項目 | FR-DRF-012、FR-APL-001–004、FR-APL-008 |
| A23 狀態檔就地修改 | 在提交的最後一次內容核對後、替換前修改原狀態檔。另先替換狀態檔，再讓 `saveAtomically` 的寫入確認失敗，於回復的最後一次內容核對後、回寫前修改狀態檔。兩次都直接改動同一檔案。若修改成功，確認套用回傳 `1`，保留外部修改，回報狀態提交或回復失敗，並回復其他可安全處理的輸出 | FR-APL-001–004、FR-APL-008、REL-002、REL-004 |
| A24 套用使用預檢版本 | 分別在預檢通過後、第一筆寫入前，以及第一筆寫入後，將後續輸出的來源換成越界連結或來源目錄內另一份內容。確認套用使用預檢確認的版本，執行時未重新開啟來源。另讓執行期參照無法取得已確認的內容，確認套用回傳 `1`，未提交新狀態，且其他可安全處理的項目已回復 | FR-MAN-005、FR-PLN-006–007、FR-APL-001–004、FR-APL-008 |
| A25 原狀態回復副本的版本 | 先載入原狀態，在擷取回復副本時就地寫入另一份格式正確的狀態，讓副本讀到改動後的內容，再於核對前改回原版本。若改動成功，確認套用辨識實際副本有誤、回傳 `1`，保留原狀態並回復其他可安全處理的輸出。另在替換狀態檔後讓 `saveAtomically` 的寫入確認失敗，分別以完整副本和遭改動的副本測試回復。完整副本須能還原原狀態。副本遭改動時，須保留現況並回報狀態無法回復 | FR-APL-001–004、FR-APL-008、REL-002、REL-004 |
| A26 不變輸出的完成判定 | 規劃一項不寫目標也不更新紀錄的「不變」輸出。分別在同批須寫入新狀態及全批免寫狀態時，於最後一次目標重檢後、批次完成前就地改動其內容。若改動成功，須保留外部修改、保留原狀態、回傳 `1` 並回復其他可安全處理的項目 | FR-APL-001–004、FR-APL-006、FR-APL-008 |

## 6. 文件對齊與交接

| 對齊事項 | 04 採用的依據與後續處理 |
| --- | --- |
| 未受管理的判定 | 依 REL-003、FR-MAN-021、SEC-002 與 §3.1。SRS 詞彙表可另行對齊，明確區分狀態紀錄、一般檔案與符號連結 |
| 整批預檢與錯誤彙整 | FR-PLN-007 的寫入前檢查是必做。S1 所述一次收集所有錯誤依 USE-004 的 `conditional` 分期 |
| 完整輸出清單、預覽與接管回報 | 05 依 §2 的查詢責任與回報內容補上介面和資料模型，對應 FR-MAN-026、FR-PLN-003、FR-MAN-019 |
| 符號連結接管與回復 | DC-003 規範套用產生一般檔案。本批若曾取代連結，觸發整批回復時須依 FR-APL-002 嘗試還原連結本身，並依 SEC-002 保護它指向的檔案。05 須驗證各平台能安全還原連結，並將無法還原的情境交由團隊確認支援條件 |
| 嚴格模式與互動 | UML S3 仍把嚴格模式優先列為提案，§12 已確認。04 採 §12，S3 註記待對齊。非嚴格模式下明確處理選項與互動提示的優先序，待互動功能納入時確認 |
| 預覽與套用的一致性 | FR-PLN-006 明列來源、本機設定及目標路徑。狀態紀錄可在目標內容不變時更新，例如接受 drift。驗證時也固定狀態、主機資訊及適用選項，由團隊確認是否在 SRS 補述比較前提 |
| 同一路徑的舊輸出與新輸出 | FR-PLN-009 涵蓋兩筆 manifest 宣告的碰撞。改名時舊輸出來自狀態檔。FR-DRF-012 與 SRS 附錄 B-6 要求自動清除未修改的舊檔，FR-DRF-013 要求保留使用者修改過的舊檔。團隊須分別決定兩類舊檔能否在同一路徑移交管理，以及同批其他輸出能否繼續套用。若採 §3.1 的整批阻擋提案，須先對齊 SRS 的清除、保留與驗收規則，再定案 A2 的預期結果 |
| 來源變更與分期 | SRS §3.2.7 簡介描述來源變更後的一般更新，FR-DRF-008 則列為 `conditional`。若考慮延後，團隊須先釐清保留已接受輸出是否需要在必做的 FR-MOD-002 增列例外，再定案 A4 的預期結果並對齊 SRS |
| 查詢驗收與分期 | FR-QRY-004 的驗收文字同時引用模組與欄位查詢。A1 將模組查詢的完整性列為必驗，欄位查詢納入時才加驗其完整性。欄位查詢延後時的正式驗收方式由團隊確認並透過 SRS 修訂 |

05 須定義設定、範本及執行介面，並完成 UML §12 的五項設計，包括接管備份的命名及保留規則、比較資料的格式與演算法、預檢後重檢與多程序協調、平台路徑與連結檢查，以及內建輸出停止管理的持久化表示。[06 測試計畫](../06-test-plan/test-plan.md)依 SRS 的需求編號及驗收條件納入 §5 的分支與故障情境。
