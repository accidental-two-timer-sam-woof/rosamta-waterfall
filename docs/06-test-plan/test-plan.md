## 1. 範圍與依據

本計畫驗收 rosamta 第一版的命令列介面、設定載入與渲染、管理、預覽與套用、drift 與清除、查詢、初始化，以及三平台的檔案操作、回復與發佈。規格以 [SRS 1.3](../02-srs/srs.md) §3 及附錄 A.3 為準。納入 117 條 essential 與 23 條 conditional 需求，共 140 條。延後的 12 條需求如下。

| 延後功能 | 需求 |
| --- | --- |
| 只管理指定欄位 | FR-MAN-014 |
| 程式與字型依賴檢查 | FR-MAN-017、FR-PLN-011–014 |
| 互動式接管、drift 處理、清除與初始化 | FR-MAN-022、FR-DRF-010–011、FR-DRF-017、FR-INI-007 |
| 以指令開啟來源檔 | FR-MAN-027 |

案例的操作與預期結果以 [詳細設計](../05-detailed-design/detailed-design.md) §4–9 為依據。§4 涵蓋服務契約，§5 涵蓋資料格式與決策表，§6–8 涵蓋平台行為、同步點與故障注入，§9 涵蓋 CLI 契約。第 5 節對照 [設計分析](../04-design-analysis/design-analysis.md) §5 的 A1–A26，第 6 節對照詳細設計 §7、§13.2 的 ASM-01–ASM-23。研究階段的候選功能透過 SRS 附錄 A 追溯。流程與類別分工可參考 [初步設計 UML](../03-preliminary-design/uml.md) 與 [詳細設計 UML](../05-detailed-design/uml.md)。

## 2. 測試方法與環境

| 層級 | 執行位置與方法 |
| --- | --- |
| 單元 | core 的 `#[cfg(test)]`。用表格案例驗證欄位、Profile、路徑正規化、位置鍵、範本引用、狀態格式與 §5.11 的各列決策 |
| 服務整合 | `rosamta-core/tests/`，以 testkit 建立測試 home、固定主機資訊與批次時間，注入 `GitClient`、`SyncHook` 或包裝真實檔案系統的 `FaultFs` |
| 平台 | platform 的測試，使用真實檔案系統與獨立程序核對檔案身分、權限、鎖定、原子替換及平台差異 |
| CLI 與驗收 | `rosamta/tests/` 啟動實際執行檔，分別擷取 stdout、stderr、exit code，並核對檔案副作用。發佈候選版再以相同執行檔執行乾淨環境、重開機與效能案例 |

每個案例使用獨立的測試 home、來源目錄、本機設定與狀態目錄。測試資料包含可跨平台重跑的主機條件、具有不同位元組與身分的對照檔，以及位於測試 home 外的獨立對照目錄。依案例記錄執行前後的存在狀態、檔案類型、身分、SHA-256、修改時間、權限或 DACL、狀態紀錄及備份位置。唯讀案例另核對未建立鎖定檔或暫存檔。預檢失敗案例同時比較所有目標與狀態檔，包含原先不存在的路徑。

### 2.1 首版驗收平台

以下為本計畫指定的首版驗收版本。各環境記錄 OS 版本及 build、CPU 架構、核心、檔案系統、帳號身分、Rust 與 git 版本。以詳細設計 §2.1 的 Rust 1.99 基準與鎖定的相依套件建置。

| 平台 | 版本與檔案系統 | 發佈目標與執行環境 |
| --- | --- | --- |
| Linux | Ubuntu 24.04 LTS，x86-64，ext4 | `x86_64-unknown-linux-musl`。CI 採 `ubuntu-24.04`，使用一般帳號 |
| macOS | macOS 15.x，Apple Silicon 與 Intel，APFS | `aarch64-apple-darwin` 與 `x86_64-apple-darwin`。CI 採 `macos-15`，另在 Intel 實機或相符架構的 runner 執行 Intel 版本 |
| Windows | Windows 11 24H2（build 26100）與 Windows Server 2025（build 26100），x86-64，NTFS | `x86_64-pc-windows-msvc`，建置使用 `-C target-feature=+crt-static`。CI 採 `windows-2025`，以標準使用者分別在開發人員模式開啟、關閉時執行。Windows 11 以相同身分與兩種模式驗收 |

在 Windows 開發人員模式關閉時，由環境管理者事先在同磁碟區準備測試連結，再由標準使用者把連結移入測試目錄。套用與回復全程以標準使用者身分執行。大小寫案例在可用的區分及不區分大小寫磁碟區分別執行。其他檔案系統的用途見 PLAT-04。

內建輸出的測試 Profile 依 05 §5.6 選擇目標。Linux 與 macOS 啟用 `ghostty`、`alacritty`、`posix-shell`，Windows 啟用 `alacritty`、`powershell`，並將 `${APPDATA}` 指向測試 home 內。合併各平台結果確認四個內建範本均有產生輸出。

### 2.2 故障注入與觀測

- I/O 失敗由 `FaultFs` 指定操作、路徑與呼叫次數。權限不足與空間不足另在受控檔案系統實測。
- 外部變動由 `SyncScript` 在 05 §8.2 指定的同步點執行，並記錄操作種類、路徑、次數、實際結果與 OS 錯誤。未到達登記的同步點即為測試失敗。平台在操作期間攔住變動時，確認阻擋理由及原指令結果，包含原先已存在的失敗。
- 實際檔案系統案例核對寫入位置、目錄及檔案身分。需證明未讀取其他位置的案例，同時觀察實際開檔與讀取，並使用內容不同的對照檔。需要獨立程序、git、另一個帳號或重開機的情境，以實際環境執行。
- 程序中止測試記錄亂數種子、終止階段和每輪結果。以實際 CLI 執行，將輸出及狀態檔的舊版、新版位元組預先存為比對基準。至少要有中止在各指定寫入階段的有效樣本，未進入該階段的執行另行計數。

## 7. 執行順序與驗收

1. **每次程式碼變更**執行單元、架構檢查、clippy 及可自動重跑的整合案例。IF-013 與 USE-001 同時使用 05 §11.3 的靜態檢查與 CLI-04 的程序觀測。
2. **整合與發佈候選版**執行三平台矩陣、Windows 兩種開發人員模式、CLI 結果契約、A1–A26 及 ASM-01–ASM-23 的適用情境。使用首版發佈成品執行重開機、乾淨環境、git 遠端、容量受限與效能驗收。
3. **驗收報告**以案例 ID 記錄需求、平台、成品 commit、步驟、預期、實際、結果與缺陷編號。故障注入附同步點和實際錯誤，程序中止附種子及有效樣本數，效能附原始時間。案例結果使用通過、失敗、阻塞或不適用。不適用需引用平台條件。

**進入條件**為首版 CLI 可建置、測試資料與預期結果已固定、測試帳號和平台就緒。**完成條件**為 140 條首版需求均有可追溯的通過證據，A1–A26 與 ASM-01–ASM-23 的適用案例均通過，並存檔第一版的範本、TOML、JSON 回歸基準。未執行或阻塞的適用案例留在待驗收清單。修正缺陷後重跑失敗案例、受影響的平台及相關回歸案例。
